# Proposal: Post-Deployment Agent Registry with Pluggable Discovery

**Author:** Varsha Prasad Narsing  
**Date:** 2026-02-16  
**Status:** Draft  
**AI Assistant:** Claude code for code review  
**Scope:** Post-deployment agent registry only (will get to pre-deployment agent artifacts in a separate proposal)

**Note:** This proposal focuses on agents as the first discoverable artifact type. The pluggable discovery design here is intentionally generic enough to extend to a broader "AI Artifact Registry" in the future, where each artifact type (agents, tools, data sources) gets its own discovery plugins and registry table while sharing the same framework.

---

## Motivation

MLflow provides registries for **prompts** (Prompt Registry) and **models** (Model Registry), 
but has no registry for **agents** - autonomous AI systems that are deployed and running in production environments.

Organizations deploy agents across diverse infrastructure: Kubernetes clusters, cloud services,
on-premise servers, and more. Today there is no unified way to:

1. **Discover** agents running in these environments
2. **Catalog** them in a central registry with metadata (tools, protocol, health)
3. **Route** requests to them through the AI Gateway with tracing, fallbacks, and traffic splitting
4. **Monitor** their availability and lifecycle (healthy, unhealthy, stale, removed)

---

## Goals

1. Provide a central, dynamic registry of live agents across any environment
2. Support pluggable discovery backends (Kubernetes, Docker, Consul, static files, etc.) - (inspired from MLflow plugin mechanism)
3. Support multiple sync mechanisms: polling, watching, and webhooks 
4. Track agent lifecycle (active, unhealthy, stale, removed)
5. Integrate with the existing AI Gateway for routing and tracing
6. Follow MLflow's established plugin patterns (entry points, registries)

## Non-Goals

1. Pre-deployment agent registry (versioning agent definitions/images) - follow up
2. Agent execution or orchestration - MLflow discovers and routes, not runs
3. Replacing existing service meshes or service discovery -- MLflow aggregates from them

## Domain Model

This section defines the core entities, their fields, relationships, lifecycle, and operations.

### What Is an "Agent" in This Registry?

An agent is a live, deployed service that:

- Accepts requests (chat messages, task instructions, tool calls)
- Acts autonomously (reasons, calls tools, produces responses)
- Runs somewhere in an environment (K8s pod, Docker container, cloud service, bare metal process)
- Is reachable via a network URL

An agent is **not** a model (static weights served via an inference endpoint), a prompt (static template text), or an artifact (versioned file in storage). It is a running process with runtime state.

### Core Entity: `Agent`

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `agent_id` | `string` | Yes (auto) | Unique identifier, e.g. `"ag-<uuid>"`. Generated by the registry on creation. |
| `name` | `string` | Yes | Unique human-readable name, e.g. `"coding-agent"`. Used in API paths and lookups. Must be URL-safe (alphanumeric, hyphens, underscores). |
| `description` | `string` | No | Human-readable description of what the agent does, e.g. `"An agent that assists with code review and bug fixing"`. Fundamental to discovery UX. |
| `url` | `string` | Yes | Network endpoint for the agent, e.g. `"http://coding-agent.agents.svc.cluster.local:8080"`. |
| `external_url` | `string` | No | Externally routable URL for the agent, if different from `url`. Required when `url` is a cluster-internal address (e.g. `svc.cluster.local`) and the Gateway needs to route from outside the cluster. |
| `protocol` | `enum` | Yes | API protocol the agent speaks. Determines how the gateway formats requests. One of: `openai-compatible`, `a2a` (Agent-to-Agent), `custom`. Default: `openai-compatible`. |
| `skills` | `list[AgentSkill]` | No | Structured capabilities the agent exposes. Each skill has an id, name, description, tags, examples, input/output modes, and parameters. See [AgentSkill](#agentskill) below. |
| `version` | `string` | No | Agent version, e.g. `"2.1.0"`. Informational; set by the source environment. |
| `health_check_path` | `string` | No | HTTP path for health checks, e.g. `"/health"`. If set, the registry periodically GETs `{url}{health_check_path}` and expects 200. |
| `source_plugin` | `string` | Yes | Which discovery plugin registered this agent, e.g. `"kubernetes"`, `"static"`. Immutable after creation. |
| `status` | `enum` | Yes (auto) | Current lifecycle state. One of: `ACTIVE`, `UNHEALTHY`, `STALE`, `REMOVED`. Managed by the registry, not set by users. |
| `verified` | `bool` | No | Whether the agent's identity has been cryptographically verified (e.g. via JWS signature + SPIFFE identity binding). Set by discovery plugins that support trust verification. Default: `null` (unknown). |
| `identity` | `string` | No | The verified identity claim for the agent, e.g. a SPIFFE ID like `"spiffe://example.org/ns/agents/sa/coding-agent"`. Set only when `verified=true`. |
| `trust_domain` | `string` | No | The trust domain the agent belongs to, e.g. `"example.org"`. Used for filtering agents by organizational boundary. |
| `metadata` | `dict[string, string]` | No | Arbitrary key-value pairs from the source environment. Plugin-specific. Examples: `{"namespace": "agents", "team": "platform", "cluster": "prod-us-east-1"}`. Used for filtering and display. |
| `last_seen_at` | `timestamp` | Yes (auto) | Last time a discovery plugin confirmed this agent exists. Updated on every sync. |
| `last_health_check_at` | `timestamp` | No | Last time a health check was performed. |
| `created_at` | `timestamp` | Yes (auto) | When this agent was first registered. |
| `updated_at` | `timestamp` | Yes (auto) | Last modification time. |

### AgentSkill

An `AgentSkill` represents a structured capability that an agent advertises. This aligns with the A2A (Agent-to-Agent) protocol's skill model used by frameworks like kagenti.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | `string` | Yes | Unique identifier for the skill, e.g. `"code-search"`. |
| `name` | `string` | Yes | Human-readable name, e.g. `"Code Search"`. |
| `description` | `string` | No | Detailed description of what the skill does. |
| `tags` | `list[string]` | No | Keywords/categories for filtering, e.g. `["search", "code", "retrieval"]`. |
| `examples` | `list[string]` | No | Example prompts or scenarios, e.g. `["Find all usages of the auth middleware"]`. |
| `input_modes` | `list[string]` | No | Accepted media types, e.g. `["text/plain", "application/json"]`. |
| `output_modes` | `list[string]` | No | Produced media types, e.g. `["text/plain", "application/pdf"]`. |
| `parameters` | `list[SkillParameter]` | No | Parameters the skill accepts. Each has `name`, `type`, `description`, `required`, and `default`. |

Using structured skills instead of flat tool name strings enables meaningful discovery queries like "find agents that can process PDF input" (`input_modes` contains `application/pdf`) or "find agents with skills tagged `code`".

### Agent Lifecycle

An agent moves through these states:

```
                 discovered by plugin
                        │
                        ▼
        ┌───────────────────────────────┐
        │            ACTIVE             │  ◄── discovered and healthy
        └───────┬───────────────┬───────┘
                │               │
        health check fails    not seen in discovery
                │               │
                ▼               ▼
        ┌───────────────┐  ┌───────────────┐
        │  UNHEALTHY    │  │    STALE      │  ◄── grace period (configurable)
        └───────┬───────┘  └───────┬───────┘
                │                  │
        health recovers      grace period expires
                │                  │
                ▼                  ▼
        ┌───────────────┐  ┌───────────────┐
        │    ACTIVE     │  │   REMOVED     │
        └───────────────┘  └───────────────┘
```

**State definitions:**

| State | Meaning | Entered when | Exited when |
|-------|---------|--------------|-------------|
| `ACTIVE` | Agent is discovered and passing health checks | First discovered, or health recovers, or re-discovered after STALE | Health check fails → UNHEALTHY, or not seen → STALE |
| `UNHEALTHY` | Agent is known but failing health checks | Health check returns non-200 or times out | Health check succeeds → ACTIVE |
| `STALE` | Agent was not reported by its source plugin in the last sync | `last_seen_at` is older than the stale grace period | Re-discovered → ACTIVE, or grace period expires → REMOVED |
| `REMOVED` | Agent is gone | Stale grace period expired, or explicit DELETE event | Can be re-created if discovered again (new `agent_id`) |

**Transitions:**

- `ACTIVE → UNHEALTHY`: Health check fails (configurable threshold, e.g. 3 consecutive failures).
- `UNHEALTHY → ACTIVE`: Health check succeeds again.
- `ACTIVE → STALE`: Agent not reported in discovery for `MLFLOW_AGENT_DISCOVERY_STALE_GRACE_PERIOD` seconds.
- `STALE → ACTIVE`: Agent re-appears in discovery.
- `STALE → REMOVED`: Stale grace period expires.
- `Any → REMOVED`: Plugin sends a `DELETED` event.

### Change Events

When the registry state changes (via sync, watch, or webhook), changes are represented as events:

| Event type | Meaning | Registry action |
|-----------|---------|-----------------|
| `ADDED` | New agent discovered | Insert as ACTIVE |
| `MODIFIED` | Agent properties changed (url, tools, version, metadata) | Update fields, keep ACTIVE |
| `DELETED` | Agent explicitly removed from source | Mark REMOVED immediately |

### Entity Relationships

```
┌──────────────┐         ┌─────────────────────┐
│    Agent     │ ──────► │  Gateway Endpoint   │  (optional auto-sync)
│              │         │  (for routing,       │
│  name        │         │   tracing,           │
│  description │         │   fallback)          │
│  url         │         └─────────────────────┘
│  protocol    │
│  skills      │         ┌─────────────────────┐
│  status      │ ──────► │  MLflow Experiment  │  (optional, for tracing)
│  verified    │         │  "gateway/{name}"    │
│  identity    │         └─────────────────────┘
│  trust_domain│
│  metadata    │         ┌─────────────────────┐
│  source      │ ──────► │  Trust Verification │  (from discovery plugin)
└──────────────┘         │  JWS signature      │
                         │  SPIFFE identity     │
                         │  binding status      │
                         └─────────────────────┘
```

- **Agent → Gateway Endpoint** (optional): When `MLFLOW_AGENT_GATEWAY_AUTO_SYNC=true`, the registry automatically creates/updates/deactivates a Gateway endpoint for each agent. This gives agents tracing, routing, and fallback for free. The Gateway should prefer routing to `verified=true` agents when multiple agents match.
- **Agent → Experiment** (optional): If the Gateway endpoint has usage tracking enabled, traces are logged to an experiment named `gateway/{agent_name}`.
- **Agent → Source Plugin** (1:1): Each agent comes from exactly one discovery source. The `source_plugin` field records this.
- **Agent → Trust Verification** (optional): Discovery plugins that support trust verification (e.g. the Kubernetes/kagenti plugin) set `verified`, `identity`, and `trust_domain` fields. This enables filtering by trust level and lets the Gateway enforce routing policies based on agent identity.
- **Agent → Other Agents** (none, for now): No agent-to-agent relationships in this proposal. Future work could add dependency/composition graphs.

### Operations

| Operation | Description | Who calls it |
|-----------|-------------|-------------|
| **List agents** | Query registry with filters (status, source, metadata) | Users, UI, orchestrators |
| **Get agent** | Look up a single agent by name | Users, gateway |
| **Register agent** | Insert or update an agent (from discovery or webhook) | Discovery plugins, sync tasks |
| **Deregister agent** | Mark an agent as REMOVED | Discovery plugins (DELETED event), manual DELETE |
| **Health check** | Probe an agent's health endpoint and update status | Periodic background task |
| **Discover** | Trigger an on-demand scan from a specific plugin with filters | Users (manual refresh) |

### Query Patterns

Users will commonly query by:

1. **Status**: "Show me all ACTIVE agents" / "Which agents are UNHEALTHY?"
2. **Source**: "Show me all agents from the `kubernetes` plugin"
3. **Metadata**: "Show me agents in namespace `agents` with label `team=platform`"
4. **Skills**: "Find agents that have a skill tagged `code-search`" / "Find agents that accept `application/pdf` input"
5. **Name**: "Get the agent called `coding-agent`"
6. **Trust**: "Show me all verified agents" / "Show agents in the `example.org` trust domain"

These patterns drive the database schema and indexing choices in the technical design.

## Python Client API

```python
import mlflow

# List all discovered agents
agents = mlflow.agents.list_agents()
agents = mlflow.agents.list_agents(status="ACTIVE", source="kubernetes")

# List agents filtered by metadata (queries the registry DB)
agents = mlflow.agents.list_agents(
    source="kubernetes",
    metadata={"namespace": "agents", "label.team": "platform"},
)

# List only verified agents in a specific trust domain
agents = mlflow.agents.list_agents(verified=True, trust_domain="example.org")

# Find agents by skill tags
agents = mlflow.agents.list_agents(skill_tags=["code-search", "retrieval"])

# Get a specific agent
agent = mlflow.agents.get_agent("coding-agent")
print(agent.description)       # "An agent that assists with code review"
print(agent.verified)          # True
print(agent.identity)          # "spiffe://example.org/ns/agents/sa/coding-agent"
print(agent.skills[0].name)    # "Code Search"
print(agent.skills[0].tags)    # ["search", "code", "retrieval"]

# Trigger on-demand discovery (calls plugin's discover() with filters)
newly_found = mlflow.agents.discover()
newly_found = mlflow.agents.discover(source="kubernetes")
newly_found = mlflow.agents.discover(
    source="kubernetes",
    filters={"namespace": "agents"},
)

# Invoke an agent (proxied through the Gateway)
response = mlflow.agents.invoke(
    "coding-agent",
    messages=[{"role": "user", "content": "Fix the bug in auth.py"}],
)
```

## Gateway Integration

Discovered agents can be automatically bridged into the AI Gateway as endpoints,
so they get tracing, routing, and fallback for free.

```
Discovery Plugin
       │
       ▼
Agent Registry (DB) - follow up with DB design
       │
       ▼ (auto-sync)
Gateway Endpoint
  name: "coding-agent"
  provider: mlflow-model-serving
  model_server_url: "http://coding-agent.agents.svc:8080"
       │
       ▼
POST /gateway/coding-agent/mlflow/invocations
  → tracing (if usage_tracking enabled)
  → auth (if auth middleware enabled?)
```

The auto-sync is opt-in via configuration:
- `MLFLOW_AGENT_GATEWAY_AUTO_SYNC=true`: Discovered agents are automatically
  registered as Gateway endpoints.
- When an agent is marked REMOVED, the corresponding Gateway endpoint is
  deactivated.

## Agent Registry Store

The registry persists agent state in the tracking database.


Note: The Prompt Registry stores prompts as `RegisteredModel` rows with a `mlflow.prompt.is_prompt=true` tag and template text in a tag value. This works because prompts are static content that rarely changes. Agents, have runtime state (url, health status, last_seen_at, source_plugin) that updates frequently and needs efficient querying (e.g. "all ACTIVE agents from the k8s plugin"). Encoding this in tags would make writes expensive and queries weird. A dedicated table gives us proper columns, indexes, and lifecycle tracking.

### Database Schema

```sql
CREATE TABLE agent_registry (
    agent_id          VARCHAR(64)  PRIMARY KEY,  -- e.g. "ag-<uuid>"
    name              VARCHAR(256) NOT NULL UNIQUE,
    description       TEXT,                       -- human-readable agent description
    url               VARCHAR(1024) NOT NULL,
    external_url      VARCHAR(1024),              -- externally routable URL (when url is cluster-internal)
    protocol          VARCHAR(64)  NOT NULL DEFAULT 'openai-compatible',
    skills            TEXT,                       -- JSON array of AgentSkill objects
    metadata          TEXT,                       -- JSON dict of metadata
    health_check_path VARCHAR(256),
    version           VARCHAR(64),
    source_plugin     VARCHAR(64)  NOT NULL,      -- which plugin discovered it
    status            VARCHAR(32)  NOT NULL DEFAULT 'ACTIVE',
    verified          BOOLEAN,                    -- NULL=unknown, TRUE=verified, FALSE=failed
    identity          VARCHAR(512),               -- verified identity claim (e.g. SPIFFE ID)
    trust_domain      VARCHAR(256),               -- trust domain (e.g. "example.org")
    last_seen_at      BIGINT       NOT NULL,      -- epoch millis
    last_health_check BIGINT,                     -- epoch millis
    created_at        BIGINT       NOT NULL,
    updated_at        BIGINT       NOT NULL
);

CREATE INDEX idx_agent_registry_name ON agent_registry(name);
CREATE INDEX idx_agent_registry_status ON agent_registry(status);
CREATE INDEX idx_agent_registry_source ON agent_registry(source_plugin);
CREATE INDEX idx_agent_registry_verified ON agent_registry(verified);
```

### Abstract Discovery Provider

Every plugin implements this interface. `discover()` is required; `watch()` is optional.

```python
class AgentDiscoveryCapability(str, Enum):
    POLL = "poll"
    WATCH = "watch"
    WEBHOOK = "webhook"

class AgentDiscoveryProvider(ABC):
    """Base class for agent discovery plugins."""

    # This is to ensure that we have live registry updates.
    # Or we can start simple with a webhook mechanism leaving the
    # onus of sending in updates to the plugin. 
    @property
    def capabilities(self) -> set[AgentDiscoveryCapability]:
        """Declare which sync mechanisms this plugin supports.
        """
        return {AgentDiscoveryCapability.WEBHOOK}

    @abstractmethod
    def discover(
        self,
        filters: dict[str, str] | None = None,
    ) -> list[DiscoveredAgent]:
        """Discover agents, optionally scoped by filter criteria.

        Required by all plugins. Used for initial sync, periodic reconciliation,
        and on-demand scoped queries.

        Args:
            filters: Optional key-value pairs that scope the discovery.
                     Keys and semantics are plugin-specific. Examples:
                       - K8s plugin:   {"namespace": "agents", "label.team": "platform"}
                       - Docker plugin: {"label.type": "agent", "network": "agent-net"}
                       - Consul plugin: {"datacenter": "us-east-1", "tag": "production"}
                       - Static plugin: (ignored, always returns full list)
                     If None, returns all agents visible to the plugin.

        Returns:
            List of DiscoveredAgent matching the filters.
        """
        ...

    def watch(
        self,
        filters: dict[str, str] | None = None,
    ) -> Iterator[AgentEvent]:
        """Stream agent changes as they happen, optionally scoped by filters.

        Optional. Only plugins with WATCH capability need to implement this.
        Must be a blocking iterator that yields events indefinitely.

        Args:
            filters: Same filter semantics as discover(). Plugins that support
                     watch should scope the watch stream to match. For example,
                     a K8s plugin with {"namespace": "agents"} would only watch
                     AgentCard CRDs in that namespace.
        """
        raise NotImplementedError(
            f"{self.__class__.__name__} does not support watch-based discovery"
        )

    def get_agent(self, name: str, filters: dict[str, str] | None = None) -> DiscoveredAgent | None:
        """Look up a specific agent by name. Optional override for efficiency;
        default implementation calls discover() and filters."""
        for agent in self.discover(filters=filters):
            if agent.name == name:
                return agent
        return None

    def health_check(self, agent: DiscoveredAgent) -> bool:
        """Check if a discovered agent is healthy.
        Default: HTTP GET to agent.url + agent.health_check."""
        if not agent.health_check:
            return True
        try:
            import requests
            resp = requests.get(
                f"{agent.url.rstrip('/')}{agent.health_check}",
                timeout=5,
            )
            return resp.status_code == 200
        except Exception:
            return False
```

### 4. Discovery Plugin Registry

Follows the same pattern as `mlflow.gateway.provider_registry` and
`mlflow.store.artifact.artifact_repository_registry`.

```python
from mlflow.utils.plugins import get_entry_points

class AgentDiscoveryRegistry:
    """Plugin-based registry for agent discovery providers.

    Plugins are loaded via Python entry points in the group
    "mlflow.agent_discovery". Each entry point name becomes the
    plugin scheme (e.g. "kubernetes", "docker", "consul", "static").
    """

    def __init__(self):
        self._providers: dict[str, AgentDiscoveryProvider] = {}

    def register(self, scheme: str, provider_cls: type[AgentDiscoveryProvider]):
        """Register a discovery provider class for a given scheme."""
        self._providers[scheme] = provider_cls()

    def register_entrypoints(self):
        """Auto-discover and register plugins from installed packages."""
        for ep in get_entry_points("mlflow.agent_discovery"):
            try:
                cls = ep.load()
                self.register(ep.name, cls)
            except (AttributeError, ImportError) as exc:
                warnings.warn(
                    f'Failed to register agent discovery plugin "{ep.name}": {exc}'
                )

    def get_provider(self, scheme: str) -> AgentDiscoveryProvider | None:
        return self._providers.get(scheme)

    def all_providers(self) -> dict[str, AgentDiscoveryProvider]:
        return dict(self._providers)

    def discover_all(self) -> list[DiscoveredAgent]:
        """Aggregate agents from all registered plugins."""
        agents = []
        for scheme, provider in self._providers.items():
            try:
                for agent in provider.discover():
                    agent.metadata = agent.metadata or {}
                    agent.metadata["_source_plugin"] = scheme
                    agents.append(agent)
            except Exception:
                _logger.warning(f"Agent discovery failed for plugin '{scheme}'", exc_info=True)
        return agents


# Module-level singleton
agent_discovery_registry = AgentDiscoveryRegistry()
agent_discovery_registry.register_entrypoints()
```


## Sync Mechanisms

### Poll-based Sync (periodic task)

Uses MLflow's existing Huey job infrastructure (`mlflow/server/jobs/`).

```python
@huey.periodic_task(crontab(minute="*/1"))  # every minute, configurable
def sync_discovered_agents():
    """Periodic task that polls all discovery plugins and syncs the registry."""
    from mlflow.agents.discovery import agent_discovery_registry
    from mlflow.agents.registry import agent_registry_store

    discovered = agent_discovery_registry.discover_all()
    agent_registry_store.sync(discovered)
```

### Watch-based Sync (background thread)

For plugins that support real-time watches (e.g. Kubernetes).

```python
def _start_watch_threads():
    """Start a background thread for each watch-capable plugin."""
    for scheme, provider in agent_discovery_registry.all_providers().items():
        if AgentDiscoveryCapability.WATCH in provider.capabilities:
            thread = threading.Thread(
                target=_run_watch_loop,
                args=(scheme, provider),
                name=f"agent-watch-{scheme}",
                daemon=True,
            )
            thread.start()

def _run_watch_loop(scheme: str, provider: AgentDiscoveryProvider):
    """Watch for agent changes and apply them to the registry."""
    while True:
        try:
            for event in provider.watch():
                agent_registry_store.apply_event(scheme, event)
        except Exception:
            _logger.warning(f"Watch for '{scheme}' failed, reconnecting in 10s", exc_info=True)
            time.sleep(10)
```

### Webhook-based Sync (REST endpoint)

For environments that push changes to MLflow.

```python
# FastAPI route
@agent_router.post("/agents/webhook/{scheme}")
async def agent_discovery_webhook(scheme: str, request: Request):

        type=AgentEventType(body["type"]),
        agent=DiscoveredAgent(**body["agent"]),
        timestamp=body.get("timestamp", time.time()),

    return {"status": "ok"}
```

## Reference Plugin: Kubernetes with kagenti AgentCard CRD

The Kubernetes discovery plugin uses [kagenti-operator](https://github.com/kagenti/kagenti-operator)'s `AgentCard` Custom Resource as the source of truth for Kubernetes-deployed agents. kagenti already handles the hard work of auto-discovering labeled workloads, fetching agent cards from `/.well-known/agent-card.json`, verifying JWS signatures against SPIRE trust bundles, and caching the result in the AgentCard's `status.card` field. The MLflow plugin reads the already-reconciled CRs rather than re-implementing this logic.

### How kagenti Works

1. A user deploys a Deployment/StatefulSet with labels `kagenti.io/type=agent` and `protocol.kagenti.io/a2a=""`
2. kagenti's `AgentCardSync` controller auto-creates an `AgentCard` CR with a `targetRef` pointing to the workload
3. kagenti's `AgentCard` controller periodically fetches the agent's card from `/.well-known/agent-card.json`, verifies its JWS signature, evaluates SPIFFE identity binding, and stores the result in `status.card`
4. The MLflow Kubernetes plugin reads these reconciled `AgentCard` CRs

### Data Model Mapping: AgentCardData → DiscoveredAgent

| kagenti AgentCardData | DiscoveredAgent | Notes |
|---|---|---|
| `name` | `name` | Direct mapping |
| `description` | `description` | Direct mapping |
| `url` | `url` | In-cluster URL (`svc.cluster.local`). Plugin also computes `external_url` if an Ingress/Route exists |
| `status.protocol` (e.g. `"a2a"`) | `protocol` | Direct mapping |
| `version` | `version` | Direct mapping |
| `skills[]` | `skills[]` | Structured mapping — see below |
| `capabilities` | `metadata["capabilities"]` | Serialized as JSON in metadata |
| `provider.organization` | `metadata["provider"]` | Provider info in metadata |
| `status.validSignature` | `verified` | Direct mapping |
| `status.signatureSpiffeId` | `identity` | SPIFFE ID from leaf cert SAN URI |
| `status.bindingStatus.bound` + `status.validSignature` | `verified` | Both must be `true` for `verified=true` |
| `spec.identityBinding.trustDomain` | `trust_domain` | From AgentCard spec or operator default |
| — | `source_plugin` | Always `"kubernetes"` |
| — | `health_check` | Derived from kagenti sync status (`Synced=True` → healthy) |

### Lifecycle State Mapping

| kagenti AgentCard State | MLflow Agent Status | Notes |
|---|---|---|
| `Synced=True` + workload ready | `ACTIVE` | Agent is discovered and healthy |
| `Synced=False` (fetch failed, workload not ready) | `UNHEALTHY` | Known but failing health checks |
| AgentCard exists but sync hasn't succeeded for N cycles | `STALE` | Grace period managed by MLflow registry, not kagenti |
| AgentCard deleted (owner workload deleted) | `REMOVED` | Garbage collected via owner references |

Note: kagenti uses Kubernetes owner references for garbage collection — when the backing Deployment is deleted, the AgentCard is automatically removed. The `STALE` grace period in the proposal lives in MLflow's registry logic, which is complementary to kagenti's approach.

### Plugin Implementation

```python
from kubernetes import client, config, watch as k8s_watch

class KubernetesAgentDiscoveryProvider(AgentDiscoveryProvider):
    """Discovers agents from kagenti AgentCard CRDs in Kubernetes.

    Supports both poll-based and watch-based sync. Reads the reconciled
    AgentCard status rather than fetching agent cards directly — kagenti
    has already done the fetching, signature verification, and identity
    binding.
    """

    capabilities = {AgentDiscoveryCapability.POLL, AgentDiscoveryCapability.WATCH}

    def __init__(self):
        try:
            config.load_incluster_config()
        except config.ConfigException:
            config.load_kube_config()
        self._custom_api = client.CustomObjectsApi()
        self._GROUP = "agent.kagenti.dev"
        self._VERSION = "v1alpha1"
        self._PLURAL = "agentcards"

    def discover(self, filters: dict[str, str] | None = None) -> list[DiscoveredAgent]:
        namespace = filters.get("namespace") if filters else None

        if namespace:
            result = self._custom_api.list_namespaced_custom_object(
                self._GROUP, self._VERSION, namespace, self._PLURAL
            )
        else:
            result = self._custom_api.list_cluster_custom_object(
                self._GROUP, self._VERSION, self._PLURAL
            )

        agents = []
        for item in result.get("items", []):
            agent = self._to_discovered_agent(item)
            if agent:
                agents.append(agent)
        return agents

    def watch(self, filters: dict[str, str] | None = None) -> Iterator[AgentEvent]:
        namespace = filters.get("namespace") if filters else None
        w = k8s_watch.Watch()

        if namespace:
            stream = w.stream(
                self._custom_api.list_namespaced_custom_object,
                self._GROUP, self._VERSION, namespace, self._PLURAL,
            )
        else:
            stream = w.stream(
                self._custom_api.list_cluster_custom_object,
                self._GROUP, self._VERSION, self._PLURAL,
            )

        for event in stream:
            event_type = event["type"]  # ADDED, MODIFIED, DELETED
            obj = event["object"]
            agent = self._to_discovered_agent(obj)
            if not agent:
                continue

            if event_type in ("ADDED", "MODIFIED"):
                agent_event_type = (
                    AgentEventType.ADDED if event_type == "ADDED"
                    else AgentEventType.MODIFIED
                )
            elif event_type == "DELETED":
                agent_event_type = AgentEventType.DELETED
            else:
                continue

            yield AgentEvent(
                type=agent_event_type,
                agent=agent,
                timestamp=time.time(),
            )

    def _to_discovered_agent(self, agentcard: dict) -> DiscoveredAgent | None:
        """Convert a kagenti AgentCard CR to a DiscoveredAgent."""
        status = agentcard.get("status", {})
        card = status.get("card")
        if not card:
            return None

        spec = agentcard.get("spec", {})
        metadata_obj = agentcard.get("metadata", {})
        namespace = metadata_obj.get("namespace", "default")

        # Determine verification status: both signature AND binding must pass
        valid_sig = status.get("validSignature")
        binding = status.get("bindingStatus", {})
        binding_bound = binding.get("bound", False) if binding else False
        verified = (valid_sig is True and binding_bound is True) if valid_sig is not None else None

        # Determine trust domain from spec or operator default
        identity_binding = spec.get("identityBinding", {})
        trust_domain = identity_binding.get("trustDomain") if identity_binding else None

        # Map skills
        skills = None
        if card.get("skills"):
            skills = [self._map_skill(s) for s in card["skills"]]

        # Build in-cluster URL from workload name
        target_ref = status.get("targetRef") or spec.get("targetRef")
        agent_name = card.get("name", "")
        url = card.get("url", "")

        # Determine health from sync condition
        conditions = status.get("conditions", [])
        synced = any(
            c.get("type") == "Synced" and c.get("status") == "True"
            for c in conditions
        )

        return DiscoveredAgent(
            name=agent_name or metadata_obj.get("name", ""),
            url=url,
            description=card.get("description"),
            protocol=status.get("protocol", "a2a"),
            skills=skills,
            version=card.get("version"),
            verified=verified,
            identity=status.get("signatureSpiffeId"),
            trust_domain=trust_domain,
            health_check=None,  # kagenti uses sync status, not a health endpoint
            metadata={
                "namespace": namespace,
                "k8s_name": metadata_obj.get("name", ""),
                "synced": str(synced).lower(),
                "provider": card.get("provider", {}).get("organization", ""),
                "capabilities": _serialize_capabilities(card.get("capabilities")),
                **({"target_kind": target_ref["kind"], "target_name": target_ref["name"]}
                   if target_ref else {}),
            },
        )

    @staticmethod
    def _map_skill(k8s_skill: dict) -> AgentSkill:
        return AgentSkill(
            id=k8s_skill.get("id", ""),
            name=k8s_skill.get("name", ""),
            description=k8s_skill.get("description"),
            tags=k8s_skill.get("tags"),
            examples=k8s_skill.get("examples"),
            input_modes=k8s_skill.get("inputModes"),
            output_modes=k8s_skill.get("outputModes"),
            parameters=[
                SkillParameter(
                    name=p.get("name", ""),
                    type=p.get("type", "string"),
                    description=p.get("description"),
                    required=p.get("required", False),
                    default=p.get("default"),
                )
                for p in k8s_skill.get("parameters", [])
            ] or None,
        )


def _serialize_capabilities(caps: dict | None) -> str:
    if not caps:
        return ""
    parts = []
    if caps.get("streaming"):
        parts.append("streaming")
    if caps.get("pushNotifications"):
        parts.append("push-notifications")
    return ",".join(parts)
```

### Integration Architectures

There are three ways to connect kagenti and MLflow, with different tradeoffs:

#### Option A: MLflow polls kagenti CRDs directly (Pull model)

The plugin implementation above uses the Kubernetes API to list/watch `AgentCard` CRs. This is the simplest approach.

- **Pro**: Standard Kubernetes pattern. MLflow only needs RBAC read access to AgentCard CRs.
- **Pro**: Watch-based sync gives near-real-time updates.
- **Con**: MLflow must run in-cluster or have kubeconfig access. Doesn't work when MLflow is a SaaS outside the cluster.

#### Option B: kagenti pushes to MLflow's webhook endpoint (Push model)

Extend kagenti's existing `MLflowReconciler` (which already auto-discovers MLflow via the `mlflows.mlflow.opendatahub.io` CRD) to POST agent events to MLflow's `POST /agents/webhook/kubernetes` endpoint whenever an AgentCard is created, modified, or deleted.

- **Pro**: MLflow doesn't need cluster access. Works with MLflow running anywhere.
- **Pro**: Leverages kagenti's existing MLflow auto-discovery infrastructure.
- **Pro**: kagenti already has the reconciled data — no double-fetching.
- **Con**: Requires handling MLflow downtime (retry queue in the operator).

This is the most natural fit for environments where kagenti and MLflow are already integrated (e.g. via the existing `MLflowReconciler` that creates experiments and injects `MLFLOW_TRACKING_URI`).

#### Option C: Hybrid — webhook push with poll fallback

kagenti pushes events to MLflow in real-time, but MLflow also periodically polls AgentCard CRs as a consistency check. This handles the case where webhook deliveries are lost.

- **Pro**: Best of both worlds — real-time updates without drift.
- **Con**: More complex. Recommended for production environments.

### Extending kagenti's MLflow Controller for Agent Registration

kagenti already has an `MLflowReconciler` that watches Deployments labeled `kagenti.io/type=agent` and:
- Auto-discovers the MLflow tracking URI via the `mlflows.mlflow.opendatahub.io` CRD
- Creates an MLflow experiment per agent
- Injects `MLFLOW_TRACKING_URI`, `MLFLOW_EXPERIMENT_ID`, etc. into agent containers
- Manages RBAC RoleBindings for agent service accounts

For the push model (Option B), this controller can be extended to also register agents with MLflow's agent registry. When an `AgentCard` transitions to `Synced=True`, the controller would POST the agent's metadata to `{mlflow_tracking_uri}/agents/webhook/kubernetes`. When an `AgentCard` is deleted, it would send a `DELETED` event. The same MLflow URI auto-discovery mechanism is reused.

```go
// Pseudocode for the extended MLflow controller
func (r *MLflowReconciler) reconcileAgentRegistration(ctx context.Context, card *v1alpha1.AgentCard) error {
    trackingURI := r.trackingURI(ctx)
    if trackingURI == "" {
        return nil
    }

    event := AgentWebhookEvent{
        Type:  "MODIFIED", // or "ADDED" / "DELETED"
        Agent: mapAgentCardToDiscoveredAgent(card),
        Timestamp: time.Now().Unix(),
    }

    webhookURL := fmt.Sprintf("%s/agents/webhook/kubernetes", trackingURI)
    return r.postWebhook(ctx, webhookURL, event)
}
```

## Compatibility and Migration

- **No breaking changes**: Agent discovery is a new, opt-in subsystem.

- **Gateway**: No changes to existing endpoint types; agents bridged as `mlflow-model-serving` provider endpoints.
- **Plugin contract**: `AgentDiscoveryProvider` is a new ABC; third-party plugins are optional.
